Architecture Reference Manual · outline

The Strata architecture

Part I, the encoding and the platformtables generated from the manual's source

Strata is a 64-bit load/store architecture with fixed 32-bit instructions, built on one idea: memory beyond the core is explicit I/O, and every storage tier is visible to software. This page is an outline of the Architecture Reference Manual: the key ideas, the rules and the tables of facts, with each heading linked to the full text in the PDF. Every instruction is described on the instruction-set page.

{{chapter:ch:intro}}

Each core has two private 64 KiB Local Stores, one for data and one for instructions. Loads, stores and instruction fetch reach nothing else. Everything beyond them, the shared cluster store, system memory and the devices, is reached by explicit, capability-checked block transfers. The design principles, as the manual states them:

{{section:ch-intro.tex:Design principles}} {{desc:ch-intro.tex:Loads and stores reach only the Local Store.}} {{section:ch-intro.tex:System organisation}}

Each core contains its integer and capability registers, its two Local Stores and its Transfer Unit. All cores share the far tiers through an arbiter. The block device is itself a node that can receive and return capabilities.

{{section:ch-intro.tex:Storage tiers}} {{table:tab:tiers}}

Two further spaces hold no storage: core-control space (space 5), through which a core stops other cores, and endpoint space (space 6), whose capabilities name nodes. The Local Store sizes are architectural; the far tier sizes belong to the platform and are reported by its platform table.

{{section:ch-intro.tex:A first program}}

The smallest complete program prints a greeting from every core in turn: code and data are in the Local Stores, output is a transfer through a capability, and cores are sequenced by passing a capability.

{{asm:ch-intro.tex:Hello from Strata core}} {{chapter:ch:state}}

All state visible to software on one core, and the little that cores share.

{{section:ch-state.tex:Per-core state}} {{table:tab:state}} {{table:tab:abi}}

The capability save table (256 entries by default; its size is a platform parameter, published in the platform table's header) is not addressable memory: capabilities can never be read or written as data, and user-mode code cannot reach it. csave and crestore name slots 0–63 with an immediate; csavex and crestorex take the slot from a register and reach every one. Each transfer names one of sixteen tags; a tag is busy from issue to completion, and because transfers are as-if-synchronous, tags affect only when a core waits, never what it computes.

{{section:sec:csrs}}

CSRs are read with csrr and written with csrw. The trap registers cause, epc, tval and tvec are banked by privilege mode. The full list, from the manual's {{pdf:app:csrs}}:

{{table:tab:csrs}} {{section:ch-state.tex:Shared state}}

All cores share T2, T3, the devices and the granule table (a generation and a head bit for each 256 KiB of memory). Nothing else is shared: no core can read another core’s registers, Local Stores, save table or inbox. The only ways to affect another core are far memory (through capabilities), gifts, revoking memory whose capabilities it holds, and a stop request through core control.

{{section:sec:reset}}

Every core starts in supervisor mode at pc = 0, with all registers, tags, the overlay map, the inbox and the save table empty, and its Local Stores loaded from the boot image. The reset capabilities:

{{table:tab:resetcaps}}

Since c0 and c1 are linear and exist only on core 0, every byte of T2 and T3 starts out owned by exactly one core.

{{chapter:ch:memory}} {{section:ch-memory.tex:The Local Stores}}

The D-LS is a 64 KiB byte-addressed memory, the only memory loads and stores reach. Accesses must be naturally aligned and inside [0, 65536), or they trap with lsfault. The I-LS is the only memory instructions are fetched from; it is filled at reset from the boot image and at run time only by tgetx. There is no address translation.

{{section:ch-memory.tex:Far spaces}}

Everything beyond the Local Stores is organised into spaces. A far location is never named by a bare address: every far access gives a capability register and an offset.

{{tabular:ch-memory.tex:Space}} {{section:sec:transfers}} {{tabular:ch-memory.tex:Instruction}}

A transfer is checked in full when it issues, in this order: the capability is live (capinv); it has the permission and names a space the transfer may use (perm); outside device space, addresses and length are multiples of 8 (xalign); the far range is inside the segment (bounds); the Local Store range is inside the Local Store (lsfault). A failing transfer traps precisely, before any byte has moved. Once issued, a memory transfer always completes: there are no asynchronous transfer errors.

{{section:sec:asif}} {{rule:ch-memory.tex:The as-if-synchronous rule}}

An implementation may perform the copy later, in the background, provided no instruction can tell the difference. It stalls every access that could observe an incomplete transfer:

{{table:tab:hazards}}

So a program may load from a buffer right after the tget that fills it, refill a buffer right after the tput that empties it, and jump to code right after the tgetx that loads it. Overlapping transfers with computation is purely a performance choice. Setting CCR.PTRAP turns the stalls into pend traps, to show where a program relies on them.

{{section:sec:devxfer}} {{rule:ch-memory.tex:One byte per beat, to consecutive offsets}}

Device registers are 8 bytes, little-endian, latched when byte 0 is read and committed when byte 7 is written; windows are read-only and byte-addressed; a transfer that starts at a stream port belongs to that stream. A read that starts at an event port (console input, the console break port, the timer’s WAIT, the display’s VSYNC, the pointer’s EVENT) is a pending device read ({{ref:sec:pendread}}): it completes only when the device has something to deliver, and meanwhile nothing else is held up.

{{section:sec:atomics}}

tamo.add, .swap, .cas, .and and .or perform an indivisible read-modify-write of one aligned doubleword at the memory that holds it. They need the A permission, which only catomic grants, and an atomic capability has no R or W: an atomic segment is reachable only through atomics. All atomics on one doubleword are linearizable.

{{section:sec:timing-visible}}

Apart from the cycle and stalls CSRs, the results of tpoll and tany, and pend traps, nothing a single core can observe depends on transfer latency or on the timing of other cores.

{{chapter:ch:caps}}

A capability is an unforgeable description of a segment of a far space and of what its holder may do with it. Capabilities live only in capability registers, in the save table, in inboxes and in the hands of devices; they never appear in memory.

{{section:ch-caps.tex:Format}} {{capfmt}} {{table:tab:perms}}

cbase, clen and cperms read the fields into integer registers; the revocable flag and the generation cannot be read. No instruction converts an integer into a capability that grants access to memory.

{{section:sec:live}} {{pseudo:ch-caps.tex:func Live}}

Every instruction that uses a capability checks Live when it executes and traps with capinv if it fails. A capability with a stale generation is dead: it behaves exactly like an empty register. Revocation therefore needs no search for copies.

{{section:sec:linear}}

A capability without D is linear: every instruction that moves it empties its source, splitting yields disjoint pieces, joining consumes an operand, and no instruction copies one.

{{rule:ch-caps.tex:Writable capabilities are linear}}

Device, core-control and endpoint capabilities are exempt and copyable: several cores may hold the console. Ordering their accesses to one device is the program’s responsibility.

{{section:sec:nooverwrite}} {{rule:ch-caps.tex:Live linear capabilities are never overwritten}} {{section:ch-caps.tex:Deriving capabilities}} {{table:tab:capops}}

Every derived capability keeps the revocable flag and generation of its source, so everything cut from a working capability dies when its granules are revoked. cshare publishes data that will never change again; catomic creates shared mutable state such as a counter or a lock word; csplit, cgive, ctake and cjoin express data-parallel work division.

{{rule:ch-caps.tex:Capabilities are 8-byte aligned}} {{section:sec:domains}}

Revocation by address lets the holder of a region of memory lend it out, in any number of pieces, shares and atomic segments, to any number of cores, and take all of it back with one instruction. Memory is divided into 256 KiB granules, each with a generation shared by all cores; a revocable capability carries the generation of its base’s granule, and revoking a range advances its granules’ generations. The number of revocable regions is limited only by memory.

{{table:tab:domtab}} {{desc:ch-caps.tex:cdom}}

A supervisor that runs a program in revocable memory lends it the working capability and keeps the revoker in its save table; crevoke or cundom recovers all of the memory when the program ends, wherever the program passed it.

{{section:sec:endpoints}}

An endpoint is a capability in space 6 that names a node. It grants no access to memory. csend (needs W) gives through it and crecv (needs R) takes from it, both in user mode. Only the supervisor makes endpoints (cmkep): they are how it lets a user program, confined to its core window, talk to exactly the nodes it chooses.

{{section:ch-caps.tex:Where capabilities live}} {{tabular:ch-caps.tex:Location}} {{chapter:ch:intercore}}

Cores share no writable memory. They cooperate by passing capabilities: a core that wants another core to see data hands over the capability for it. The hand-over is both the communication and the synchronisation.

{{section:sec:inbox}}

Nodes 0…N−1 are the cores and node N is block device 0. Every core’s inbox keeps a separate two-entry FIFO queue for each node that may give to it.

{{desc:ch-intercore.tex:cgive cs, rx}} {{section:sec:publication}} {{rule:ch-intercore.tex:The publication rule}}

So a producer can fill a buffer with tputs and immediately cgive it; the consumer may tget from it as soon as it has taken it. No fences, flags or locks, and since there are no caches, no coherence traffic.

{{section:ch-intercore.tex:Deterministic fan-in}}

An any-sender ctake returns the gift of the lowest-numbered sender that has already delivered, which depends on timing. To collect results deterministically, take from each sender explicitly:

{{asm:ch-intercore.tex:collect:}} {{section:sec:supervised}}

An operating system runs a program written for the bare machine, which assumes it is core 0 of N and that halt ends it, on a subset of the cores in user mode. CSRs corebase and corecount define a window of physical cores; inside it, coreid, ncores, cgive and ctake see window-relative numbers. The program’s halt traps to the supervisor.

{{rule:ch-intercore.tex:The inbox belongs to the supervisor}}

The priv trap is also what lets a supervisor run bare-machine programs unchanged: it emulates the trapping inbox instruction on a queue of gifts it keeps for the program.

{{chapter:ch:swmanaged}}

Strata has no hardware caches. When a program’s access pattern is regular it streams data with transfers; when it is irregular, it builds a cache in its D-LS. Two hardware assists make the common operations cheap without taking policy away from software.

{{section:sec:swcache}} {{tabular:ch-swmanaged.tex:CSR}}

ltag looks a far offset up in the tag table: on a hit it returns the D-LS address of the cached byte, on a miss the victim line’s address with bit 63 set. linst installs the tag. A miss is handled by ordinary code, and because of the as-if-synchronous rule the load after the fill is always correct:

{{asm:ch-swmanaged.tex:load_cached:}} {{section:sec:overlays}}

Code that does not fit in the I-LS lives in far memory and is copied in with tgetx. The sixteen-entry overlay map lets a program call such code by its far address, with the hardware taking the fast path when it is resident:

{{desc:ch-swmanaged.tex:xcall}}

A miss handler loads the code with tgetx, maps it with xmap and returns with eret, which re-executes the xcall. With xslot set ({{ref:sec:xslot}}) the map pages fixed-size code units into I-LS slots, and calls made from paged code leave far links that xret resolves, so the overlay map becomes demand paging for code with the policy entirely in software. StrataOS pages most of its own kernel this way.

{{chapter:ch:traps}}

Two privilege modes, a small set of banked trap registers, and no interrupts. A trap is the synchronous transfer of control that occurs when an instruction cannot complete. The only asynchronous event that changes a core’s control flow is a stop request sent through core control, delivered as a trap at an instruction boundary.

{{section:sec:modes}} {{tabular:ch-traps.tex:Bit}}

Authority over memory and devices is never a matter of mode: it comes from the capabilities a core holds. User mode differs from supervisor mode in exactly these operations:

{{table:tab:userlimits}} {{section:sec:trapentry}} {{pseudo:ch-traps.tex:func Trap(c, value)}}

halt, stop, priv and svc always reach the supervisor. A trap is precise: the trapping instruction has had no architectural effect and does not retire.

{{section:ch-traps.tex:Causes}}

The trap causes and what tval holds for each, from {{pdf:app:causes}}:

{{table:tab:causes}}

At most one trap is taken per instruction: a pending stop request first (in user mode), then ifault, then illegal, then the instruction’s own checks in the order of its Exceptions table on the instruction-set page.

{{section:sec:svc}}

svc is the one instruction whose purpose is to trap: from user mode it enters the supervisor with cause svc. Supervisor calls are few, because authority comes from capabilities: a program reads a file by sending a message to a server through an endpoint, a user-mode instruction.

{{section:sec:corectl}}

Core-control space has one doubleword per core. A tput of a doubleword with bit 0 set to offset 8n sends a stop request to core n: a user-mode core traps to its supervisor with cause stop, even while it waits. This is the only forced preemption; there is no timer interrupt.

{{section:sec:events}}

A device “interrupts” by completing a transfer: the core asks for the event by issuing a transfer the device completes only when the event happens.

{{tabular:ch-traps.tex:Event}}

tany waits for the first of several such events: bits 15:0 of its operand select tags, bit 16 the inbox. The StrataOS system core sleeps on a pending timer read and its inbox at once:

{{asm:ch-traps.tex:ev_wait:}} {{rule:ch-traps.tex:One release completes every pending break read}} {{chapter:ch:model}}

What a program can rely on when transfers have latency and cores run concurrently, and why the architecture guarantees it. The sequential semantics 𝒮 is the one the reference emulator implements: an interleaving of the cores’ instructions, each memory transfer performed completely at the instant it executes. An implementation such as the RTL performs transfers in the background and runs cores truly concurrently.

Corollary 2 is a property of the instruction set, not a discipline: a racy program cannot be written. The proof sketches are in the PDF.

{{section:sec:determinism}} {{rule:ch-model.tex:Theorem 2 (multicore timing independence)}}

The project’s cross-checking tool relies on Theorem 2: it runs each example on the emulator and the RTL, whose timing is completely different, and requires identical output, halt states and per-core instruction traces.

{{chapter:ch:encoding}} {{section:sec:formats}}

Every instruction is one 32-bit little-endian word on a 4-byte boundary. Bits 31:26 hold the primary opcode; the rest follows one of six formats. In the diagrams, coloured fields are fixed opcode or function values and are checked; shaded fields are reserved, ignored by implementations and written as zero by software.

{{section:sec:memmap}} {{table:tab:memmap}}

The framebuffer window is ordinary memory in every architectural respect: reached by transfers through capabilities cut from the memory root, split, given, shared like any other.

{{section:ch-platform.tex:Device space}} {{table:tab:devmap}}

Every port, register and window starts at a multiple of 8, so a capability can be cut to exactly one of them. The console’s output port is the one every core holds from reset, in c2.

{{section:sec:timer}} {{table:tab:timer}}

Waiting for a point in time is a transfer like any other event: write DEADLINE, start a read of WAIT on some tag, and wait for the tag with tany.

{{asm:ch-platform.tex:dlbuf}} {{section:sec:fbctl}}

The framebuffer is the top 16 MiB of system memory, scanned out live; ownership is by capability, like all memory. The controller has two registers:

{{table:tab:fbctl}} {{section:sec:pointer}}

A mouse or touchpad over the display: a read of EVENT waits for the next event (a move, a button, the wheel, entering or leaving the display), each 8 bytes carrying the position and the buttons; STATE reads where the pointer is now. Moves coalesce, so a slow reader sees where the pointer went, never a backlog of where it was.

{{table:tab:pointer}} {{section:sec:blkdev}}

The block device can touch far memory only through a capability that a core gives it: handing over the buffer capability is the DMA permission, and the device hands it back when the command completes. While the device holds the buffer no core can touch it, so DMA protection holds by construction.
