THE SERVERS

Everything but the kernel's mechanisms is a user process that answers messages. Here is each one, and every message it accepts.

A server is an ordinary time-shared process that the kernel marks as one of its core's servers (up to four): a request that arrives at that core goes to the one its header word 48 names (0x53 << 56 | index; anything else names index 0, the server the core is known by). Its loop is RECEIVE, serve, REPLY (os/lib/srv.s). A program reaches a server through an endpoint, by convention in a fixed register (c1 proc, c2 fs, c3 tty, c4 pipe) or one proc gives it by name (LOOKUP "dev", "ws", "net").

Every message is specified field by field in os/spec/, one file per server; these pages and the manual's chapter are generated from those files. A test checks each file against the code: its ops must be exactly those the server's dispatch answers, and the OP_* constants of os/lib/sys.s must agree. An op's name links to its handler; data offsets count from the start of the data (offset 64 of the buffer); hover an error code for its general meaning.

01proc — processes and names

pid 1, made by the kernel at boot, alone on core 1. The first process the kernel creates. It is the only holder of the kernel's endpoint apart from dev, so it is the only process that asks for processes to be created and destroyed. It keeps the process tree, exit statuses, interrupt flags and the name registry, and starts tty, pipe and the login shell. Spawning is MEMORY (an arena from the kernel), the start-up block written into it, fs LOADIMG (the program image read straight into the arena), DUPS at the servers of the handles passed, then CREATE; meanwhile the caller's SPAWN stays parked.

5SPAWNStart a program

The program is the command's first word (1..24 bytes): a path, or a name looked for in the caller's current directory, then in /bin, then in /sys; when it is found in /bin or /sys that path becomes the command's first word. proc gets an arena from the kernel (MEMORY), writes the start-up block into it (pid, parent, the three descriptors, the command), has fs load the image (LOADIMG), tells fs the child starts in the caller's tag path (CWD mode 2), sends DUPS to fs, tty and pipe for the handles passed, and asks the kernel to CREATE the process. The caller is the child's parent. A command whose first word is exactly ws is made the server of the lowest empty core, a busy one (CREATE flag bit 14: its clients, term, are placed on other cores); exactly net, the server of the lowest empty core and alone on it (proc keeps the endpoint CREATE gives it, parked in the kernel, to send it CANCEL and CLEANUP; with no room to park it, that net is stopped again and SPAWN answers −7). Both stay ordinary children (WAIT, KILL and Ctrl-C work) and may REGISTER. A bare-metal image (no "SYS2" marker) runs as N threads, one on each of N contiguous cores without a server (N = 1 if the thread count is 0); a file as its handle 0 is copied into its arena first (fs READALL to 0x80000, a0 = its length), and a file as its handle 1 gets its output at exit (0xC0000, as many bytes as the exit code, at most 64 KiB; the status becomes 0).

02dev — the device manager

pid 2, made by the kernel at boot, on core 2. It holds the device root, describes the platform, and cuts device capabilities out of the root for the servers that own a device: the console's ports for tty, the disk's ports and node for blk, the network interface for net, the framebuffer for ws. The framebuffer memory is the kernel's: dev asks for it with FBLEND, which revokes every older capability to it, and passes it on. It also gives every program the wall clock (TIME): the timer's EPOCH and ZONE, which a program adds to its own reading of NOW.

03fs — files, tags and the store

pid 3, made by the kernel at boot, on core 3, alone there from 8 cores. The file system: it keeps its files in the store of copy-on-write trees that db keeps, as a client of it. A file has one name and carries tags, and a directory is the set of its files' tags. Programs are files: proc has fs load them into new arenas. Every call answers −5 when the disk cannot be read as a store or a page fails its checksum.

The disk is a store: copy-on-write B+trees in namespaces, and a change is on the disk whole or not at all. The store is another server's, db, which reaches the disk through blk; fs is its client. A file has one name and carries tags; the set of its tags is its directory, and a name is unique within a directory. A path is components separated by / (empty ones are skipped): the last is the file's name, the ones before it the tags of its directory, in any order. A path that does not start with / is read under the requester's current tag path (CWD); . and .. are resolved. A path is at most 376 bytes, and so is the whole data of TAG, UNTAG, RENAME and SETATTR (−1 beyond; LOADIMG: −4). Every call but READBLK answers −5 when the disk cannot be read as a store, a page fails its checksum or the device refuses a command; a call that changes the disk answers −1 when the disk is full, and what it had changed is given up. Up to 16 files are open at a time, across all programs.

10From proc and the kernel

Three messages go from proc to the servers that keep something per process, and one from the kernel to proc.

proc sends DUPS to the servers of the handles a child inherits, CLEANUP to fs, tty, pipe and net, CANCEL to tty, pipe and net. The servers do not check that these come from proc. proc holds no register for net's endpoint: it keeps the one CREATE gave it parked in the kernel, and sends to net only after net's REGISTER mode 1 (net makes no calls to proc after that, so proc, which waits for the answer, cannot wait for a net that waits for proc). ws answers CLEANUP, but proc sends it none: ws collects the clients it started itself. dev answers all three with 0 and does nothing.
