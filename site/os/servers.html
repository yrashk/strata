THE SERVERS

Everything but the kernel's mechanisms is a user process that answers messages. Here is each one, and every message it accepts.

A server is an ordinary time-shared process that the kernel marks as its core's server: every request that arrives at that core goes to it. Its loop is RECEIVE, serve, REPLY (os/lib/srv.s). A program reaches a server through an endpoint, by convention in a fixed register (c1 proc, c2 fs, c3 tty, c4 pipe) or one proc gives it by name (LOOKUP "dev", "ws", "net").

The tables are generated from the sources each time the site is built (tools/web-os.py): the op numbers from each server's dispatch code, which decides what it answers, and the text from the comment that documents the op, where the op's name links. A test fails when a dispatched op has no description, when a description names an op the dispatch does not answer, when an OP_* constant of os/lib/sys.s names an op its server does not answer, or when these pages fall behind the sources. Hover an error code for its meaning.

01proc — processes and names

pid 1, the first process the kernel creates. It is the only holder of the kernel's endpoint apart from dev, so it is the only process that asks for processes to be created and destroyed. It keeps the process tree, exit statuses, interrupt flags and the name registry, and starts tty, pipe and the login shell. Spawning is MEMORY (an arena from the kernel), the start-up block written into it, fs LOADIMG (the program image read straight into the arena), DUPS at the servers of the handles passed, then CREATE; meanwhile the caller's SPAWN stays parked.

02dev — the device manager

pid 2. It holds the device root, describes the platform, and cuts device capabilities out of the root for the servers that own a device: the console's ports for tty, the disk's ports and node for fs, the network interface for net, the framebuffer for ws. The framebuffer memory is the kernel's: dev asks for it with FBLEND, which revokes every older capability to it, and passes it on. It also gives every program the wall clock (TIME): the timer's EPOCH and ZONE, which a program adds to its own reading of NOW.

03fs — files, tags and the store

pid 3. It owns the block device and keeps the disk as a store of copy-on-write trees; the file system is one client of it. A file has one name and carries tags, and a directory is the set of its files' tags. Programs are files: proc has fs load them into new arenas. Every call answers −5 when the disk cannot be read as a store or a page fails its checksum.

04tty — the console

pid 4, started by proc. It owns the console (output, input, the break port) and the pointer, whose events it hands to the window server. It never blocks on a device: the break read is always in flight and one byte of input is read only while a reader waits, and its RECEIVE names both tags. Cooked mode echoes and edits a line; raw mode gives whatever bytes are there. Ctrl-C asks proc to SIGNAL the foreground process.

05pipe — pipes

pid 5, started by proc. Up to 8 pipes, each a 2 KiB ring in the server's own data memory; the read end of pipe p is id 2p+1, the write end 2p+2. The ends are reference counted per process, so a pipe sees the end of its input when no writer is left. Each pipe holds at most one waiting reader and one waiting writer, parked.

06net — IPv4, ICMP, UDP, TCP

Started on demand (net ADDRESS, or by the first program that uses the network): proc makes a program named exactly net the server of the lowest empty core. The interface carries raw IPv4 packets. Four sockets, each with a 2 KiB receive ring and a 2 KiB send buffer; TCP retransmits after 250 ms, doubling up to 8 s; DNS over UDP with a cache. A socket belongs to the process that made it.

07ws — the window server

Started from a shell: proc makes a program named ws the server of the lowest empty core, and it registers as "ws". The only process that touches the framebuffer and, while it runs, the keyboard. Clients draw in their own arenas and lend each finished band of pixels with DAMAGE. More on its own page.
