01What it is built on

StrataOS runs on Strata's machine as it is, not on an imitation of a conventional one. The four things a conventional kernel hides are each in plain view.

Memory is explicit I/O

A core's loads and stores reach only its own 64 KiB Local Stores. A process's far memory is its arena, 1 MiB by default; reading or writing it is a tget or tput. Saving a process at a switch is a transfer of exactly the bytes it uses, and the kernel counts them.

Capabilities name everything

An arena, a message buffer, a window of device ports, an endpoint to a server's core: each is a capability in a register, and nothing else grants access. Writable memory is linear, never copied; it moves. Revocation by address takes back an arena and everything cut from it in one step.

A microkernel that passes messages

The kernel creates processes, hands out memory, keeps time and moves messages. Files, the console, pipes, the network, windows and process management are servers: user processes. A message is a 4 KiB buffer lent to the server and given back with the answer.

Preemption with a visible price

Every 2 ms (configurable from 100 µs to 100 ms) the system core stops each worker that has more than one thread to run. A switch copies the outgoing thread's Local Store out and the next one's in: the cache flush other CPUs hide. ps, cores and the window server show the switches and the kilobytes moved.

02Cores and their roles

The kernel is not one program on one core. It is the system core (core 0), which runs no programs, and a dispatcher on every other core, the supervisor code that runs that core's threads. The two halves share one table in the cluster store and talk through job records and doorbells.

Who runs where

  • System core (core 0): creates and destroys processes, places them on cores, cuts arenas out of the pool and revokes them, holds the only DEADLINE register (the preemption tick and every timed wait), answers the operations of its endpoint, which only proc and dev hold.
  • Dispatchers (every worker core): run that core's threads, take every capability that arrives in the core's inbox and hand it to the right process, emulate the inbox instructions user code may not execute (ctake, cpoll, tany), and page code units in on a miss.
  • Server cores: a core can have up to four servers; a request names one by its index in header word 48 (0x53 << 56 | index; without it, the core's first). The kernel creates proc, dev and fs on cores 1, 2 and 3, blk beside dev and db on core 5; proc starts tty and pipe on the next free ones, so pipe joins db. Servers are ordinary time-shared processes; other programs share their cores, except where a server keeps a device read waiting (tty, net), and fs from 8 cores on, so that db can trust what fs forwards to it.
  • Threads: a StrataOS program is one thread. A program run with -n N, or a bare-metal example, gets N threads (at most 6) on N contiguous cores without a server, seen through the corebase/corecount window exactly as on the bare machine; cgive between them goes straight from core to core.

03Where everything lives

Three tiers, each with a fixed purpose: system memory (T3) for arenas and the framebuffer, the cluster store (T2) for what is the kernel's for good, and each core's Local Stores for the code and data that run now.

A process

A process owns one arena: a run of whole 256 KiB granules, 1 MiB unless the spawner asked for more (the shell's -m N), zeroed when it is handed out. The program's memory is its c0; the parts the kernel needs sit at the arena's top. When the process ends the system core revokes the arena by address: every capability based there, whatever was cut from it or lent out, dies at once.

04From the boot ROM to the shell

Every core starts in the boot ROM. Core 0 brings the system up far enough to load the file server, and the file server loads everything else.

  1. Boot ROM, core 0. Verifies the platform table, finds block device 0, checks the boot header, checks that the images fit the machine's Local Stores, and loads them. On any failure it says why and every core halts.
  2. Boot ROM, every core. Takes read-only shares of the images, copies the kernel to I-LS 0x4000 and D-LS 0xA000, and jumps to it. Core 0 alone keeps a share of the kernel's far image in c12, from which it pages its own code.
  3. The system core makes the framebuffer window and the arena pool revocable regions, builds the KST, gives each worker a copy with a core-control capability and the clock, and reads the boot manifest.
  4. The servers. The kernel creates dev, blk, db, fs and proc: proc, dev and fs on cores 1, 2 and 3, blk beside dev, db on core 5. dev gets the device root, blk asks it for the disk, db keeps the store on it and fs the file system on db; one that asks another before it runs asks again a tick later. proc starts tty and pipe on the next free cores, then the login shell, which runs /etc/rc.
