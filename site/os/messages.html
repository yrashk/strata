MESSAGES

A message is not copied anywhere. It is a 4 KiB buffer the client owns, lent to a server as a capability and given back with the answer filled in.

01The buffer

Every program owns one message buffer, c5, the last 4 KiB of its arena. A request is a 64-byte header and up to 4,032 bytes of data written into it with tput; the reply is the same buffer, read back with tget.

op
what to do; the numbers are per server (the catalogue)
handle
which open file, pipe end, socket or window; for some ops a pid, a port or a cursor
length
the bytes of data, or a count the op defines
mode
flags; bit 0 is "do not block" for the reads that would wait
result
≥ 0 success; −1 failed, −2 interrupted, −3 would block, −4 no such file or program, −5 no free core / not allowed, −6 no memory, −7 busy, −8 timed out
pid
the sender, written by the receiving core's dispatcher

Attachments

A request may carry one more capability: a piece of the arena for fs to load a program into, a band of pixels for the window server. A reply may carry two: an endpoint from LOOKUP, device ports from dev. A request's attachment reaches the server in c7; a reply's arrive in the caller's c6 and then c7. A client attaches with svc SEND, which sends the attachment and the buffer with nothing of that core in between: the receiving dispatcher pairs an attachment with the next message from the same core.

02A round trip

A program on one core asks a server on another. Each core's dispatcher sorts whatever arrives in its inbox by what it is: a buffer it knows as one of its processes' is a reply, an unknown 4 KiB buffer is a request for its server.

How the dispatcher sorts its inbox

  1. A piece of the arena of a process being created on this core (its base is in the job record the system core posted): installed in the new thread.
  2. A capability whose base is a local process's message buffer: that process's reply.
  3. A capability whose base a local process named in WAIT_REPLY: it goes to that process (the window server's keyboard buffer works this way).
  4. From a core inside the window of a local multi-threaded process: a gift between its threads, queued for the emulated ctake.
  5. Any other 4 KiB memory capability: a request for one of the core's servers (up to four; header word 48 = 0x53 << 56 | index names one, anything else the first), queued with the attachment waiting from the same core; its sender's pid is stamped from the buffer's memory. With no such server here, or a full queue, it goes back at once with −1.
  6. Anything else: an attachment, which travels with the next message from its core.

Who sent a capability and what memory it is decide everything. A process cannot forge another one's request or reply, because it does not hold the memory that identifies them.

03Doorbells, parking, dying

  • Doorbells. Without one, a busy destination core would notice the message at its next tick. With one it is a stop request in that core's core-control word, and its dispatcher runs at once.
  • Parking. A server that cannot answer yet (a reader of an empty pipe, a WAIT for a child still running, an EVENT with no event) PARKs the request: the kernel keeps the buffer, the server goes on serving others, and UNPARKs it to answer later. The client simply stays blocked in its WAIT_REPLY.
  • Waiting on several things. A process blocks in one svc at a time. A client sends a request the server holds until something happens; a server's RECEIVE takes a timeout and a mask of transfer tags. Nothing busy-waits.
  • When a client dies while a server works on its request, the request dies with the client's arena: the server's next transfer through it faults, and the server library's guard drops it and returns to the loop.
  • When a server ends (the window server is started and stopped by the user), the requests queued or parked at it go back to their senders with −1.
  • Forwarding. A server may pass a request on instead of answering it: REPLY with another server's core as the token gives the buffer there, where it is a request like any other, its sender stamped from the buffer: the program, not the server that forwarded it. The forwarding server does not wait. Who answers, and to which core, is the two servers' agreement: fs forwards a program's DBGET, DBSCAN and DBBATCH to db with the program's core in header word 56, and db takes that word only from a request that comes from fs's core (where nothing else runs, from 8 cores on) and is not fs's own, and answers the program itself: three messages and no copy, where relaying is four and two copies.

04What a round trip costs

The kernel copies nothing: the 4 KiB buffer changes hands as a capability, and the only bytes moved are the ones each side transfers itself, the 64-byte header and the data. What a round trip costs is counted in traps and transfers:

wherewhat happens
clienta tput of the header (and data), a csend, one svc that sends, rings and blocks
server corea dispatcher entry on the doorbell; RECEIVE returns; the server's tget of the header, its work, a tput of the result, one svc REPLY that gives the buffer back and rings
client corea dispatcher entry on the doorbell, which recognises the reply and resumes the client; a tget of the result
switchesnone if the server was waiting on its core and the client's core had nothing else to run; otherwise a context switch on that side, priced as on the kernel page

So a request and its reply are four dispatcher entries and two doorbells, plus the switches the cores' other threads cause. In the RTL measurements of the kernel's switch work an average trap, switches included, took about 15,000 cycles; cores shows the current figures per core, and ps each process's switches and kilobytes moved.
